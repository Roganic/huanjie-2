- 产品目标：验证 AI GM、简化规则和长流程跑团体验。目标用户、单局时长和 MVP 成功标准仍在 `product.md` 中待定。

- 后端：Python、FastAPI 单体；规则裁定、角色和装备、战斗、法术、场景、NPC、存档和模组。
- 行动主链路：前端输入 → `/action` → 动作识别与规则编排 → 状态变更 → 叙事生成 → 前端刷新。
- 模型主要负责裁定后的叙事；动作路由依赖请求字段及关键词逻辑，尚不能据此视为完整自由决策的 AI GM。
- 规则方向是“5e 判定语法 + OSE 流程结构”，并非完整复刻原版规则。代码已经扩展了战士、法师、盗贼及职业能力。
- 记忆已有近期行动和叙事历史上下文；本次未发现完整向量检索 RAG 主链路。
- 状态以进程内会话和 JSON 存档为主；当前适合本地原型。

## 关键断点

1. **模组前后端未接通。** `app/frontend/src/App.tsx` 的 fetchModules / activateModule 仍返回 MOCK_MODULES；后端已有 `src/routers/modules.py`，但相关接口和推进测试仍失败。界面上的模组选择不能当作真实战役已加载。
2. **AI 已有接入，待验证可用质量。** `src/agent/providers/` 已有 Kimi/OpenAI，`src/agent/narrator.py` 已有约束校验、重试和模板回退。TASKS 中“接入 Kimi”落后于代码；更准确的下一步应是验证真实模型链路、错误提示和叙事质量。当前 SSE 是完整结果生成后分块发送，不能等同模型逐 token 输出。
3. **重复实现提高整合成本。** 存在多套战斗、状态、记忆、场景入口，以及同名文件和包。`main.py` 显式依赖路由注册顺序覆盖重复端点。前端 App.tsx 3420 行、后端 state.py 1541 行、orchestrator.py 1159 行，后续修复需先确定实际运行路径。
4. **验收口径不可靠。** CHECKPOINTS 后期以“失败数不增加”判定通过，且记录过 47/54 个失败；不代表整套系统通过。本次结果再次表明需要重建可复现基线。
5. **文档与实现不同步。** ai-architecture.md 还写后端只有入口和健康检查；共识写“不做 GitHub Pages”，仓库实际已有 Pages 部署工作流。应以代码与验证结果为准，再回写文档。

## 建议的下一阶段

以“一名玩家可连续玩完一个短篇战役”为候选目标，建议先用 20–30 分钟作为讨论起点，而非既定要求。

1. 固定依赖与失败基线，清理测试收集阻断，逐项区分过期契约和真实缺陷。
2. 接通真实模组，验证创建角色 → 加载战役 → 探索/NPC → 战斗 → 结局 → 保存/恢复。
3. 配置真实模型进行多轮试玩，检查叙事与状态一致、上下文延续和回退行为。
4. 根据试玩结果决定自由输入、规则复杂度、记忆策略和内容扩展；暂不建议先堆更多职业或 RAG 基础设施。

需与用户确认：优先追求固定剧本的稳定体验，还是 AI 自由主持的开放探索？二者会影响下一阶段的验收口径与开发顺序。
