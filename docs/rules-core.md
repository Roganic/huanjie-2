# 规则内核

阅读顺序：先看“V1 摘要”和“核心循环”，只有在准备实现时再看“模块边界”和专题文档。

本文件用于沉淀“适合 AI 跑团”的第一版规则内核，而不是摘录原版规则书全文。

## V1 摘要

- 核心底盘采用轻量 d20 检定
- 结构上更接近 OSE：规则短、裁定清楚、例外少
- 表达上借用 5e 的现代玩家习惯：属性修正、优势 / 劣势、统一难度语言
- 第一版只保留 AI 容易稳定执行的高频环节：检定、战斗、伤害、资源消耗、短状态
- 长列表法术、复杂职业特性、细碎例外先不进入内核

## 设计原则

- 简单、稳定、可执行
- 让模型负责叙事，让系统负责裁定
- 优先保留高频、易懂、易实现的机制
- 复杂例外和高负担联动延后
- 能转成明确数据结构的机制优先

## 当前方向

- 以轻量 d20 体系为基础
- 吸收 5e 的玩家认知优势
- 吸收 OSE 的简洁和可执行性
- 强主题机制后续以模块形式加入

## OSE 对 V1 的主要贡献

- 强化“先声明行动，再做必要判定”的流程，而不是把所有行为都变成技能按钮
- 保留资源压力：生命、物品、时间、照明、补给都应影响探索节奏
- 维持低例外密度，避免大量只在少数场景出现的修正规则
- 让战斗结算尽量短，减少模型在多轮流程中的状态漂移
- 鼓励裁定优先于规则查表，但裁定入口必须标准化

## V1 核心循环

1. 玩家声明行动
2. GM agent 判断是否自动成功、需要检定，或直接触发固定规则
3. 规则引擎产出结构化结果：成功 / 失败 / 代价 / 伤害 / 状态 / 资源变更
4. GM agent 将结果转成叙事反馈，并推进场景状态

这个循环里，系统只负责回答“怎么判”，不负责生成长篇叙事。

## V1 必须落地的机制

### 属性与检定

- 使用少量基础属性和对应修正值
- 默认检定公式应统一，避免同时存在多种底层判定法
- 只有在结果不确定且后果明确时才投骰
- 难度分级应少而稳定，便于模型长期记忆

### 优势 / 劣势

- 作为第一版的唯一通用情境修正
- 不叠加多个来源，只保留“有利 / 不利 / 抵消”三态
- 用它替代大量细碎数值修正

### 战斗与伤害

- 一轮只保留少量动作类型
- 命中、伤害、护甲、防御应当一眼可判
- 避免复杂借机、反应链和多段触发
- 伤害结果优先影响生命、状态和资源，不引入过多子系统

### 状态效果

- 第一版只保留少数高频状态，例如受限、倒地、失能、濒危
- 每个状态只写一个核心效果，避免长说明
- 状态应支持回合结束、休整或特定条件解除

### 资源与成长

- 至少追踪生命、关键物品槽、时间消耗和基础恢复
- 成长先做低复杂度方案，例如场次或里程碑推进
- 职业、专长、法术树等高组合内容先不进入内核

## 暂不纳入 V1 的内容

- 大规模技能列表
- 高频查表的子系统
- 长法术清单与完整魔法经济
- 复杂职业构筑
- 密集的位移、反应和连锁触发
- 需要持续维护大量隐藏状态的机制

## 模块边界

- 内核负责：检定、战斗、伤害、状态、资源、恢复
- 场景模块负责：探索、潜行、追逐、社交压迫感等专题流程
- 世界观模块负责：职业包装、阵营语义、特殊设定
- 扩展模块负责：法术、怪物模板、强主题系统

## 实现提示

- 数据结构应优先围绕“动作输入”和“裁定结果”设计
- 每次裁定的输出最好是结构化对象，而不是自然语言片段
- 如果一个机制难以在三句话内解释清楚，默认不进入 V1 内核
